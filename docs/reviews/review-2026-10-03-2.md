## Summary

The project follows SOLID better than most: services receive their repositories, clocks, prompters and clients; interfaces are small (`Aead`, `Digest`, `Pick<Reporter, …>`); the server's layers depend on `repositories.ts`, not on Drizzle. I found no Critical or High problem in this category. The seven findings are the places where the project breaks its own rule ("takes everything it needs as arguments, so every OS can be tested on any OS") or where a Claude Code feature leaked into the generic interfaces. Two are Medium because they have a cost today: a few modules build real system access inside their logic, which is one reason the Windows launcher bug (BUG-01) could not be caught by a test on another OS, and the "claude.ai skills" option is wired through four generic types, which every future agent would have to carry.

## Findings

### SOLID-01 · Medium · Dependency Inversion: managed-settings access is created inside the logic, in three places

- [x] **Where:** `packages/cli/src/agents/claude-code/after-restore.ts:79-81`; `packages/cli/src/agents/claude-code/claude-code-adapter.ts:72-74`; `packages/cli/src/app.ts:180-187`
- **Problem:** `detectManagedSettings` takes a `ManagedSettingsSystem` interface (good), but each caller builds the real one itself with `nodeManagedSettingsSystem(...)` instead of receiving it. `AfterRestoreDeps` has no slot for it.
- **Why it matters:** Any test that reaches the plugin step of after-restore (`packages/cli/test/claude-code-after-restore.test.ts:167`) reads the real PC: `/etc/claude-code` or `C:\Program Files\ClaudeCode`, and on Windows it runs `reg query` twice. On a PC with organization-managed Claude Code the test sees different input than on CI. It is also three copies of the same wiring (the `agents` command builds a second detector system just for this).
- **Fix:** Create it once in `createClaudeCodeAdapter` and pass it down:

  ```ts
  const managed = () =>
    detectManagedSettings(
      options.managedSystem ?? nodeManagedSettingsSystem(env, baseDir, platform),
    );
  // AfterRestoreDeps: readonly managedSettings: () => Promise<ManagedSettings>
  ```

  Let `inspector.notices` accept `'agents'` (see ARCH-01), so `app.ts` no longer builds its own.

- **Effort:** S
- **Confidence:** high (the effect on a managed PC is by reading, not observed)

### SOLID-02 · Medium · Interface Segregation / Open-Closed: a Claude-only option lives in the generic interfaces

- [x] **Where:** `packages/cli/src/agents/adapter.ts:38` (`CollectOptions.includeAccountSkills`), `:103` (`AgentInspector.accountSkills`), `:124` (`AfterRestoreContext.accountSkills`); `packages/cli/src/cli/commands.ts:22,38`; `packages/cli/src/cli/program.ts:141-147,179-185`; `packages/cli/src/push/push-command.ts:296-319` (with the "claude.ai" wording); `packages/cli/src/pull/pull-command.ts:361`
- **Problem:** "A copy of your claude.ai skills" is a Claude Code feature (T42), but it was added as a named field to the collector options, the inspector, the after-restore context, both command option types, and as an `if` block inside generic `push`.
- **Why it matters:** The next agent-specific opt-in (for example another agent's "sync my prompts library") means editing the same six generic places again, and every adapter must accept options it never uses. This is the same root as ARCH-01, seen from the interface side.
- **Fix:** Let an adapter declare its optional parts as data, and keep the generic code a loop:

  ```ts
  interface OptionalPart {
    readonly id: string; // 'account-skills'
    readonly scope: 'global' | 'project';
    available(): Promise<{ names: readonly string[]; problem: string | null }>;
    question(names: readonly string[]): string;
  }
  // AgentAdapter: readonly optionalParts?: readonly OptionalPart[]
  // CollectOptions / AfterRestoreContext: readonly include: ReadonlySet<string>
  ```

  Keep the `--account-skills` flag names; map them to the id in `program.ts`.

- **Effort:** M
- **Confidence:** high

### SOLID-03 · Low · Dependency Inversion: some modules use the host's globals and path rules instead of the injected ones

- [x] **Where:** `packages/cli/src/agents/claude-code/plugin-sync.ts:3,63,229` (host `join` and `extname`, while every other adapter file picks `win32`/`posix` from the injected platform); `packages/cli/src/env/shell-profile.ts:190` (`process.env`); `packages/cli/src/secrets/file-store.ts:57` (`process.env['SystemRoot']`)
- **Problem:** The project's rule is that the OS, the home folder and the environment are passed in (`AppEnvironment`), so any OS can be tested on any OS and live tests can run with a temporary environment. These three spots read the real process instead.
- **Why it matters:** `createClaudeCli` decides "is this a `.cmd` launcher?" with the host's `extname`, so the Windows branch cannot be unit-tested on Linux or macOS; that is part of why BUG-01 went unseen. `realPowerShell` passes the real `process.env` to PowerShell even when the CLI was started with a replaced environment.
- **Fix:** Give `createClaudeCli` and `readCurrentPlugins` the platform (they already get `env` / `baseDir`), and pass `env` into `realPowerShell` and `windowsOwnerOnly` from the composition root.
- **Effort:** S
- **Confidence:** high

### SOLID-04 · Low · Liskov Substitution: the no-terminal prompter cannot stand in for a prompter without callers checking for it

- [x] **Where:** `packages/cli/src/ui/no-terminal-prompter.ts:21-31`; the special cases at `packages/cli/src/pull/pull-command.ts:307-326` and `packages/cli/src/push/push-command.ts:230-252,375`; `packages/cli/src/ui/prompter.ts:47` (`canAsk`)
- **Problem:** `createNoTerminalPrompter` implements `Prompter` by rejecting every method. To keep a command from stopping halfway, push and pull each carry a hand-written `checkAnswerable` that must know every question the later code might ask, guarded by `prompter.canAsk === false`.
- **Why it matters:** Each new question has to be added to those pre-checks by hand. Forgetting one brings back finding 24 of the threat model (a command that stops after writing some files); nothing in the types catches it. The pre-checks also repeat the conditions of the real questions, so the two can drift.
- **Fix:** Make the split structural rather than a flag: a _plan_ step that receives the prompter and returns every answer (`PullPlan`, `PushPlan`), and an _apply_ step whose parameters do not include a prompter at all. Then "asked before anything changes" is enforced by the compiler for every prompter, and `canAsk` and both `checkAnswerable` functions can go. Pull is already close (`prepareOne` → `applyOne`); the conflict resolver, after-restore and env questions are what still ask during apply.
- **Effort:** M
- **Confidence:** high

### SOLID-05 · Low · Single Responsibility: `file-gathering.ts` is two modules, and `restorer.ts` carries the `~/.claude.json` merge

- [x] **Where:** `packages/cli/src/agents/claude-code/file-gathering.ts:168-234` (`parseSettings`, `commandsInSettings`, `commandWords`, `programOf`) next to the file walker at `:55-166`; `packages/cli/src/agents/claude-code/restorer.ts:174-277`
- **Problem:** `file-gathering.ts` reads files from disk _and_ parses settings JSON and command lines. Seven modules import it only for the pure parsing (`hook-scripts.ts`, `restore-rules.ts`, `restorer.ts`, `auto-memory.ts`, `command-review.ts`, both collectors). In `restorer.ts`, about 100 of 445 lines are the `~/.claude.json` merge with its own backup and "Claude is running" loop.
- **Why it matters:** Pure rule files (`restore-rules.ts`, `command-review.ts`) depend on a module that imports `node:fs`; a change to how settings commands are parsed and a change to how links are followed land in the same file. The `.claude.json` merge has different rules from every other file, which makes `restore` harder to follow (and to move behind an adapter method later).
- **Fix:** Move the four parsing functions to `settings-commands.ts` (no Node imports). Move `readClaudeJson`, `mergeInto` and `mergeClaudeJson` to `claude-json-merge.ts`, taking `writeAtomically` and the running check as parameters.
- **Effort:** S
- **Confidence:** high

### SOLID-06 · Low · Interface Segregation: `DetectorSystem` is wider than what most of its users need

- [x] **Where:** `packages/cli/src/agents/claude-code/detector.ts:19-31`; users `programs.ts:28`, `after-restore.ts:54`, `findExecutable` at `detector.ts:68-95`
- **Problem:** `findExecutable` needs `platform`, `homedir`, `env` and `isExecutable`; `createProgramLocator` adds `readText`. Both take the whole `DetectorSystem`, which also has `isDirectory` and `runVersion`.
- **Why it matters:** Tests for after-restore and programs must build a full fake detector system (`claude-code-after-restore.test.ts:18`) with methods the code under test never calls. Small cost, but it is paid in every new test.
- **Fix:** Narrow the parameter types: `findExecutable(system: Pick<DetectorSystem, 'platform' | 'homedir' | 'env' | 'isExecutable'>, …)` and the same idea for the locator. No runtime change.
- **Effort:** S
- **Confidence:** high

### SOLID-07 · Low · Open/Closed: merge strategies are not the plug-in point the architecture doc says they are

- [x] **Where:** `packages/core/src/merge.ts:15` (`MergeStrategyName` union); `packages/core/src/merge-strategies.ts:18-22` (fixed `MergeStrategies` object) and `:133-140` (`selectMergeStrategy`)
- **Problem:** ARCHITECTURE.md §12 lists merge strategies as something that "plugs in behind interfaces; nothing existing changes". Each strategy has `appliesTo(path)`, but the choice is hard-coded: JSON merge if its `appliesTo` says yes, else side by side.
- **Why it matters:** Adding a merge for another format (TOML for a future agent, or Markdown sections) means editing the name union, the `MergeStrategies` type, the factory and `selectMergeStrategy`. No cost today; it becomes one with the second agent, whose settings may not be JSON.
- **Fix:** For the "merge" choice, take an ordered list and pick the first that applies: `mergeStrategies.find((strategy) => strategy.appliesTo(path)) ?? textSideBySide`, with the list passed in by the adapter's restorer. Make `name` a `string`.
- **Effort:** S
- **Confidence:** high

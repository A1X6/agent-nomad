## Findings

### Bugs

### BUG-01 · High · Windows: programs started through a `.cmd` launcher always fail

- [x] **Where:** `packages/cli/src/agents/claude-code/plugin-sync.ts:216-262` (`createClaudeCli`); used by `packages/cli/src/agents/claude-code/after-restore.ts:66,125` (npm) and `:86` (claude)
- **Problem:** For a `.cmd`/`.bat` path it runs `execFile('cmd.exe', ['/d', '/s', '/c', '"<path>"', ...args])`. Node escapes the quotes inside that argument, so cmd.exe receives `\"C:\...\npm.cmd\"` and cannot find it. Reproduced on this PC with the same call: `'\"C:\nvm4w\nodejs\npm.cmd\"' is not recognized as an internal or external command`, exit code 1.
- **Why it matters:** On Windows `npm` is always `npm.cmd`, so "Install it with `npm install -g …`?" after a pull always ends in "Could not install". Plugin reinstall fails the same way when Claude Code was installed with npm (`claude.cmd`); the native `claude.exe` is not affected.
- **Fix:** Build the command line yourself and pass it verbatim:

  ```ts
  execFile('cmd.exe', ['/d', '/s', '/c', `""${claudePath}" ${args.join(' ')}"`], {
    ...options,
    windowsVerbatimArguments: true,
  });
  ```

  Extend the `CMD_UNSAFE` check to refuse arguments with spaces too (they are joined unquoted). Add a Windows-only test that runs a real `.cmd` (see QA-01).

- **Effort:** S
- **Confidence:** high (reproduced)

### BUG-02 · Medium · Server: no error handler on the database pool

- [x] **Where:** `packages/server/src/server.ts:46`; `packages/server/src/main.ts`
- **Problem:** `new Pool(...)` has no `pool.on('error', …)`. The Neon driver's docs (checked through Context7) register one in every `Pool` example: an idle client whose connection drops emits `error` on the pool, and an `error` event with no listener is thrown by Node as an uncaught exception.
- **Why it matters:** A dropped idle WebSocket (Neon compute suspending, a network blip) can stop the API process. Render restarts it, but requests in flight fail and the next one waits for a cold start.
- **Fix:** `pool.on('error', (error) => logger.error('pool_error', describeError(error)));` right after creating the pool. Optionally add `process.on('unhandledRejection' / 'uncaughtException')` in `main.ts` that log and exit, so a crash is at least one clear log line.
- **Effort:** S
- **Confidence:** medium (documented behaviour; not observed in the Render logs, which I did not read)

### BUG-03 · Medium · `push` and `pull` exit 0 when a setup was skipped or refused

- [x] **Where:** `packages/cli/src/push/push-command.ts:215-220` (newer copy on the server), `:382-387` (partial pull), `:412-418` (over 5 MB, even printed as an error); `packages/cli/src/pull/pull-command.ts:254-257` (older copy); `packages/cli/src/cli/run.ts:59-61`
- **Problem:** These paths print a warning or error and `continue`/`return`. The handler then resolves, and `runCli` returns `EXIT.ok`.
- **Why it matters:** `agentnomad push --global --yes` in a script or cron reports success although nothing was saved. Section 10 of ARCHITECTURE.md promises exit code 1 for "failed".
- **Fix:** Collect skipped setups in the handler and throw one error at the end (for example a `PartialResultError` listing them) so `runCli` returns 1; keep processing the remaining setups first. Decide whether "skipped on purpose by `--yes`" should be 1 or a new code, and document it.
- **Effort:** S
- **Confidence:** high

### BUG-04 · Medium · Pull replaces a symlinked file with a plain file

- [x] **Where:** `packages/cli/src/agents/claude-code/restorer.ts:126-140` (`writeAtomically`), called at `:376`
- **Problem:** The existing file is read with `stat`/`readFile` (which follow links), then the new content is written to a temp file and `rename`d onto the path. Renaming onto a symlink replaces the link itself.
- **Why it matters:** People who keep `~/.claude/settings.json` or `CLAUDE.md` as links into a dotfiles repo (stow style) lose the link on the first merge or overwrite; the dotfiles copy silently stops being updated. The shell-profile writer already handles this (`shell-profile.ts:139-146`, T46), and push follows such links, so the restorer is the odd one out.
- **Fix:** As in the profile writer: `lstat` the destination, and when it is a link write to `realpath(destination)` instead. Add a POSIX test next to the existing "writes through a linked profile" one.
- **Effort:** S
- **Confidence:** high

### BUG-05 · Low · The home folder is only blocked as a project in the menu

- [x] **Where:** `packages/cli/src/push/push-command.ts:141-147`; `packages/cli/src/pull/pull-command.ts:264-265`

Push then saves the global setup under project rules (which do not exclude `skills/synced`, so organization and Anthropic claude.ai skills are saved, against T42's rule). Pull merges a project's `.claude/settings.json` into the global settings.
- **Fix:** One shared check used by both commands: refuse a project scope when `cwd` is the home folder (and when it is Claude Code's base folder), with a message to `cd` into the project.
- **Effort:** S
- **Confidence:** high

### BUG-06 · Low · Local state: any read error counts as "no state", and writes are not serialized

- [x] **Where:** `packages/cli/src/state/local-state.ts:83-89` and `:97-118`
- **Problem:** `load()` returns an empty state for _any_ `readFile` error (permissions, a locked file), and the next `update()` then writes that empty state over the real file. Two agentnomad commands running at once also overwrite each other (read, change, write with no lock).
- **Why it matters:** Lost revisions mean a later push sends `expectedRevision 0` and gets a confusing "deleted since this PC last had it" conflict, and lost `#partial` notes remove the T46 protection.
- **Fix:** Only treat `ENOENT` as empty (the same fix T46 made in `shell-profile.ts`); rethrow anything else. The race is rare; a note in the docs is enough unless it shows up.
- **Effort:** S
- **Confidence:** high

### BUG-07 · Low · A well-formed cursor with an impossible date gives a 500

- [x] **Where:** `packages/server/src/db/bundle-cursor.ts:14-17`; `packages/server/src/db/bundle-repository.ts:73`
- **Problem:** The cursor check is a shape regex (`\d{4}-\d{2}-\d{2} …`), so `2026-13-45 99:99:99+00` passes and Postgres then fails the `::timestamptz` cast. That error is not an `InvalidCursorError`, so the route answers 500 and logs `unhandled_error`.
- **Why it matters:** Only a logged-in user can trigger it and nothing leaks, but it is noise in the error log. Also, ARCHITECTURE.md calls cursors "tamper-checked"; they are format-checked only (harmless, since the query is scoped by user id).
- **Fix:** After the regex, check `!Number.isNaN(Date.parse(updatedAt.replace(' ', 'T')))`, or catch Postgres error class `22` in `list` and throw `InvalidCursorError`. Reword the doc line.
- **Effort:** S
- **Confidence:** medium (by reading; not executed)

### BUG-08 · Low · Windows: an npm-installed Claude Code is not seen as running

- [x] **Where:** `packages/cli/src/agents/claude-code/running-claude.ts:30-37` and `:48-54`
- **Problem:** On Windows the process list is `tasklist` program names only. Claude Code installed with npm runs as `node.exe`, which `isClaudeProcess` cannot recognise (the `@anthropic-ai/claude-code` test needs a command line, which only `ps` provides).
- **Why it matters:** Pull then merges `~/.claude.json` while Claude Code is open, and Claude Code can write its own copy back over it, the exact case T43 guards against.
- **Fix:** On Windows read command lines too, e.g. PowerShell `Get-CimInstance Win32_Process | Select-Object -ExpandProperty CommandLine`, falling back to `tasklist`.
- **Effort:** S
- **Confidence:** medium (not tested with an npm install of Claude Code)

### SEC-01 · Medium · The pull review misses settings that redirect or loosen Claude Code without running a program

- [x] **Where:** `packages/cli/src/pull/command-review.ts:119-178`; `packages/cli/src/env/loader-variables.ts:7-8`
- **Problem:** The review lists hooks, command settings, loader variables, `bypassPermissions` and MCP servers. A merged `settings.json` can also carry, unreviewed and even with `--yes`:
  - `env` entries that are not "loaders" but change where data goes or how tools start, e.g. `ANTHROPIC_BASE_URL`, `HTTPS_PROXY`, `NODE_EXTRA_CA_CERTS`, `PATH`;
  - `permissions.allow` rules (e.g. `Bash`), `permissions.additionalDirectories`, and a relaxed `sandbox` block: the same effect as `bypassPermissions` for the tools they name.

  The `LOADER_VARIABLE` list used for saved environment values also misses several variables that make programs run code: `NODE_PATH`, `PYTHONHOME`, `JAVA_TOOL_OPTIONS`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_CONFIG_GLOBAL`, `EDITOR`/`VISUAL`/`PAGER`, `LESSOPEN`, `BASH_FUNC_*`.

- **Why it matters:** A compromised PC could send every prompt and the API key to its own server, or let Claude run shell commands unasked on the user's other PCs, through a `pull --yes` that is documented as "never accepts new commands".
- **Fix:** In `settingsEntries`, also report as new/changed: any `env` name matching a "redirect" list, `permissions.allow` entries that are new on this PC, `additionalDirectories`, and `sandbox` changes. Extend `LOADER_VARIABLE`. Check each key against Claude Code's settings reference first (the project's rule), and add the keys to the drift check's watch list.
- **Effort:** M
- **Confidence:** medium (the gap in the code is certain; which keys Claude Code honours from which file needs the docs check)

### SEC-02 · Low · Scripts are recognised only by file extension in the review

- [x] **Where:** `packages/cli/src/pull/command-review.ts:215-241` (`isScript`, `scriptsRun`)
- **Problem:** A changed file is listed as "script" only when it has one of the 16 extensions. A file with no extension inside a synced folder (e.g. `skills/tool/bin/run`, restored because the folder is taken whole) that a hook already on this PC runs is written without being shown.
- **Why it matters:** The same "changed script behind an unchanged hook" case that finding 2 of the threat model closed, for extensionless executables.
- **Fix:** In `scriptsRun`, match any incoming file whose path a command word names (keep the extension test only for the "scripts next to it" rule), or treat files with the executable bit or a `#!` first line as scripts.
- **Effort:** S
- **Confidence:** medium

### Database and queries

### DB-01 · Low · Upload runs the usage and metadata queries twice, one after another

- [x] **Where:** `packages/server/src/bundles/bundle-service.ts:149-150`; `packages/server/src/db/bundle-repository.ts:114-120` and `:173-181`
- **Problem:** `bundles.usage()` and `bundles.get()` are independent but awaited in sequence, and the same count/sum query is written twice (in `usage` and inside `putMeta`). One PUT is about nine round trips to Neon.
- **Why it matters:** Latency only; the pre-check is deliberate (refuse before storing 5 MB) and the transaction is correct.
- **Fix:** `const [used, current] = await Promise.all([bundles.usage(userId), bundles.get(input.key)])`, and one private `usageQuery(db | tx, userId)` used by both places.
- **Effort:** S
- **Confidence:** high

### DB-02 · Low · Expired sessions and the orphan sweep

- [x] **Where:** `packages/server/src/db/session-repository.ts:57-71` (only called from login, `auth-service.ts:148`); `packages/server/src/storage/postgres-blob-store.ts:41-55`
- **Problem:** Expired sessions are deleted only when that same user logs in again, so sessions of users who never return stay forever. The orphan sweep filters `bundle_blobs` by `created_at`, which has no index, so it scans the table (about 1 save in 50).
- **Why it matters:** Slow growth and an occasional slow save; nothing breaks at today's size.
- **Fix:** Add a global `delete from sessions where expires_at <= now()` to the existing random prune (it already runs for `rate_limits`), with an index on `sessions.expires_at`; add an index on `bundle_blobs.created_at` when the table grows.
- **Effort:** S
- **Confidence:** high

### DB-03 · Low · Register writes the user and the first session in two separate statements

- [x] **Where:** `packages/server/src/auth/auth-service.ts:125-134`
- **Problem:** If `sessions.create` fails after `users.create`, the account exists but the client gets a 500 with a normal error body, which the CLI shows as "Something went wrong on the server. Try again later" (not the "could not confirm" message); trying again says "username taken".
- **Why it matters:** Rare and recoverable with `agentnomad login`, but the message points the wrong way.
- **Fix:** Wrap both inserts in one transaction (add a `registerWithSession` to the repository layer), or in the CLI treat a 5xx on register as `OutcomeUnknownError` even when it carries an error body (`http-api-client.ts:125-132`).
- **Effort:** S
- **Confidence:** high

### Best practices

### BP-01 · Low · Key handling is not the same in the three auth commands

- [x] **Where:** `packages/cli/src/auth/auth-commands.ts:184-200` (register), `:221-246` (login), `:288-306` (account delete)
- **Problem:** Account delete wipes `authKey` and `passwordKey`; register and login wipe only `passwordKey`, and login does not wipe `dataKey` when saving the session throws. When login succeeds on the server but the data key cannot be unlocked, the new server session is left behind unused.

- **Fix:** One `withDerivedKeys(password, salt, params, async (keys) => …)` helper that always wipes both keys in `finally`; call `api.auth.logout()` (best effort) before throwing the "could not be unlocked" error.
- **Effort:** S
- **Confidence:** high

### System design

### ARCH-01 · Medium · Generic push and pull import Claude Code modules directly

- [x] **Where:** `packages/cli/src/push/push-command.ts:21` (`unknownEntriesNotice`) and the Claude wording at `:292` and `:313`; `packages/cli/src/pull/pull-command.ts:13` (`agentVersionNotice`) and `:193` (`~/.claude.json`); `packages/cli/src/pull/command-review.ts:4-10` (the whole review is built on Claude Code's settings format); `packages/cli/src/app.ts:12-17,180-187` (the `agents` command builds Claude's managed-settings notice itself, because `inspector.notices` only accepts `'push' | 'pull'`)
- **Problem:** ARCHITECTURE.md rule 4 says "Push, pull, encryption and the server do not know what Claude Code is", and ADDING-AN-AGENT.md says a new agent is "a new folder plus one line". Today the review of runnable things, the unknown-files text, the version notice and several prompts are Claude Code code called from the generic commands.
- **Why it matters:** The second agent (on the roadmap) would get Claude Code's review rules applied to its files, or none, and that review is the main safety step of pull.
- **Fix:** Add to `AgentAdapter`/`AgentInspector`: `reviewRunnable(incoming, current): ReviewedEntry[]`, `describeConflict(path)`, `versionNotice(saved, here)`, and let `notices` accept `'agents'`. Move `command-review.ts` into `agents/claude-code/`. Keep the two helper functions that are truly generic (`unknownEntriesNotice`, `compareVersions`) in `agents/`.
- **Effort:** M
- **Confidence:** high

### ARCH-02 · Low · The database layer writes CLI help text, and the service imports it from the repository module

### QA and testing

### QA-01 · Medium · The code that starts real programs has no tests

- [x] **Where:** `createClaudeCli` (`plugin-sync.ts:224-262`), `realPowerShell` (`shell-profile.ts:185-196`), `windowsOwnerOnly` (`file-store.ts:55-62`), `systemProcessLister` (`running-claude.ts:28-42`), `readRegistry` (`managed-settings.ts:206-221`): none is referenced in any test; the e2e steps (`packages/e2e/src/steps.ts`) have no plugin or program install.
- **Problem:** Everything around them is tested through injected fakes, which is right, but the thin real implementations are exactly where OS quoting and PATH rules bite.
- **Why it matters:** BUG-01 has been broken on Windows since it was written, with 1002 passing tests.
- **Fix:** A small `system.test.ts` with `it.runIf(win32)` / `it.runIf(posix)` cases that really run: a temp `.cmd` that echoes its arguments (through `createClaudeCli`), `realPowerShell` with a `Write-Output`, `systemProcessLister` returning a non-empty list, `windowsOwnerOnly` on a temp file. CI already runs on all three OSes.
- **Effort:** S
- **Confidence:** high

### QA-02 · Low · CI does not run the dependency audit or the migration check

- [x] **Where:** `.github/workflows/ci.yml`; `packages/server/package.json:19` (`db:check` exists but nothing calls it)
- **Problem:** The threat model lists "`pnpm audit` clean" as a control, but it only runs by hand. `drizzle-kit check` (migrations consistent with each other) is never run.
- **Fix:** Add `pnpm audit --prod` and `pnpm --filter @agentnomad/server db:check` to the check job (the audit as a weekly scheduled job too, so a new advisory is noticed without a push).
- **Effort:** S
- **Confidence:** high

### QA-03 · Low · No coverage numbers and no unused-code check

- [x] **Where:** `vitest.config.ts`; root `package.json`
- **Problem:** There is no way to see which lines the 1002 tests miss, and unused exports were not checked in this review either (every `src` file is re-exported from `index.ts`, which hides them from the compiler).
- **Fix:** Turn on Vitest's coverage report in CI (report first, a threshold later). Consider `knip` as a dev dependency; this needs your OK as a new dependency.
- **Effort:** S
- **Confidence:** high

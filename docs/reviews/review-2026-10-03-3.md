## Findings

### Bugs

### BUG-09 · High · Ctrl+C at a pull conflict question does not stop the pull

- [x] **Where:** `packages/cli/src/agents/claude-code/restorer.ts:404-409` (the per-file `catch`); the questions asked inside it at `:241` and `:356` (`onConflict`) and `:249` (`onClaudeRunning`)
- **Problem:** Each file is restored inside `try { await restoreEntry(file) } catch { skipped + warning }`, so one bad file never stops the rest (T43). But the questions are asked inside that same `try`. When the user presses Ctrl+C or Esc, the prompter throws `PromptCancelledError`; the `catch` turns it into the warning `Skipped "rules/a.md": Cancelled.` and the loop goes on to the next file.
- **Reproduced:** the restorer on a temp folder with two differing files and one new file, and a resolver that cancels: `restore` finished normally, asked both questions, and wrote the new file (`written: ["rules/c.md"]`, `skipped: ["rules/a.md", "rules/b.md"]`).
- **Why it matters:** Ctrl+C is how a user says "stop, I picked the wrong setup or folder". Here the pull keeps writing every file that has no conflict, asks the next question, then records the revision as pulled and moves on to plugins. The user has to press Ctrl+C once per differing file. The same `catch` swallows `AnswerNeededError`: with no terminal, a question that the pre-check missed (BUG-10 is one) becomes a "Skipped" warning and exit code 0.
- **Fix:** Let errors from the questions pass through, without making the restorer know the UI classes:

  ```ts
  let stopped: unknown;
  const ask: ConflictResolver = (path, question) =>
    onConflict(path, question).catch((error: unknown) => {
      stopped = error;
      throw error;
    });
  // … use `ask` instead of `onConflict`, wrap onClaudeRunning the same way …
  } catch (error) {
    if (stopped !== undefined) throw stopped;
    report.skipped.push(file.path);
    // …
  }
  ```

  Add a restorer test: a resolver that rejects makes `restore` reject, and no later file is written.

- **Effort:** S
- **Confidence:** high (reproduced)

### BUG-10 · Medium · Scripts saved with other line endings conflict on every pull

- [x] **Where:** `packages/cli/src/agents/claude-code/restorer.ts:72-83` (`lineEndingsFor`) and `:341-354` (the comparison); `packages/cli/src/pull/pull-command.ts:307-318` (the no-terminal pre-check compares the unconverted bytes); `packages/cli/src/push/bundle-files.ts:74-90`
- **Problem:** Before comparing with the file on disk, the restorer converts the incoming copy: `.sh .bash .zsh .fish .py .rb .pl .lua` to LF on every OS, `.bat .cmd` to CRLF on Windows. The file on disk is compared as it is. So a script that is stored with the "other" line ending (a `.py` hook with CRLF on Windows, which is what Git's `autocrlf` produces; or an LF `.cmd`) never equals its own saved copy.
- **Reproduced:** `hooks/check.py` with CRLF on disk and the byte-identical file as the incoming entry: one conflict question, and with "merge" the result is `check.py.agentnomad-incoming-20261003T112615Z` next to an unchanged file.
- **Why it matters:** On that PC every pull asks "check.py already exists here and is different", although nothing changed. `pull --yes` leaves one more `…agentnomad-incoming-…` copy per pull; `--overwrite` rewrites the user's file with other line endings and makes a backup each time. Without a terminal the pre-check says "nothing to ask", then the restorer asks anyway (see BUG-09 for what happens then).
- **Fix:** Treat the file as unchanged when it equals the incoming copy before **or** after conversion:

  ```ts
  } else if (sameBytes(existing, content) || sameBytes(existing, file.content)) {
    return;
  }
  ```

  and use the same rule in pull's `checkAnswerable` (best: export one `sameForRestore(platform, path, existing, incoming)` from the restorer and call it in both places). Add the test above.

- **Effort:** S
- **Confidence:** high (reproduced)

### BUG-11 · Medium · The remembered revisions belong to the server, not to the account

- [x] **Where:** `packages/cli/src/app.ts:123-129` and `packages/cli/src/state/local-state.ts:102` (state is kept per server host); `packages/cli/src/auth/auth-commands.ts:140-154` (`logOut`) and `:239-242` (login saves the new session) never touch it; only account delete does (`:308`). Used at `packages/cli/src/pull/pull-command.ts:250-257`, `packages/cli/src/push/push-command.ts:408-409`, `packages/cli/src/commands/setup-commands.ts:121-145`
- **Problem:** `state.json` remembers `claude-code/global → revision` under the server's host name. Project keys differ per account (they are a keyed hash), but `global` is the same word for every account. After `logout` and `login` as another account (work and personal, or a new account after the old one was deleted from another PC), the old account's number is still there.
- **Why it matters:** With the old account at revision 7 and the new one at revision 2:
  - `pull` warns "revision 2, older than revision 7 that this PC already had … or the server is sending an old copy", and `pull --yes` **skips the global setup** (the rollback guard, T38).
  - `push` sends `expectedRevision 7`, gets a conflict and asks "A newer copy … was saved from another PC. Replace it?"; `push --yes` skips it.
  - `status` shows "this PC has revision 7, the server 2", and one "was deleted on the server" line per project of the old account. A `#partial` note carries over too.
- **Fix:** Remember which account the revisions belong to. Smallest change: add an optional `username` to the server section of `state.json`; when a login or register succeeds with another username (or none is stored), clear `revisions` and keep `projects`. Clearing on `logout` alone is not enough, because an expired session is dropped by `withSession` without a logout. Add a test: login A, push, logout, login B, pull → no "older copy" warning.
- **Effort:** S
- **Confidence:** high (by reading; the three effects follow directly from `revisionOf` returning the old number)

### BUG-12 · Medium · macOS and Linux: saved environment values are written to the shell profile again on every pull

- [x] **Where:** `packages/cli/src/env/env-restore.ts:33-34` ("already set" looks only at this process's environment); `packages/cli/src/env/shell-profile.ts:138-175` (always makes a backup and writes, even when the block would not change); `packages/cli/src/pull/pull-command.ts:319-324` (the no-terminal pre-check uses the same test)
- **Problem:** A value added to `~/.zshrc` is not in the environment of the terminal that ran the pull, and never in a shell that does not read the profile (cron, CI, most `ssh host command` calls). The next pull there finds the variable "missing" again.
- **Why it matters:**
  - Interactive: the same "Add 2 variables?" question on every pull until a new terminal is opened.
  - `pull --yes` from cron or a script: every run rewrites the profile and leaves a new `~/.zshrc.agentnomad-backup-<time>` (a full copy of the profile, values included). They pile up without limit.
  - Without a terminal and without `--yes`: the pull stops with "Add X?" every time, although X is already in agentnomad's block.

  Windows is not affected in the same way (no backup file), but it also rewrites the user variables each time.

- **Fix:** Before asking, read the profile's agentnomad block (`readBlock` already exists) and count a name whose value is already there as set. In the writer, return early with `backup: null` when `upsertBlock(...)` equals the existing text. Give `EnvWriter` a `current(): Promise<ReadonlyMap<string, string>>` so `restoreEnvValues` and pull's pre-check share one test.
- **Effort:** S
- **Confidence:** high (by reading; this code path cannot run on this Windows PC)

### BUG-13 · Low · Any program called `claude` counts as "Claude Code is running"

- [x] **Where:** `packages/cli/src/agents/claude-code/running-claude.ts:48-54` (`isClaudeProcess`), with the Windows list at `:30-37`
- **Problem:** A process counts when its file name is `claude` or `claude.exe`. The Claude desktop app is `Claude.exe` on Windows and `…/Claude.app/Contents/MacOS/Claude` on macOS; after lower-casing, both match. On macOS and Linux the first word of the command line is taken, so a `claude` under a path with a space (`/Users/John Smith/.local/bin/claude`) is **not** seen.
- **Why it matters:** With the desktop app open, `pull --yes` always leaves `~/.claude.json` alone (MCP servers and preferences are never restored), and an interactive pull asks the user to close "Claude Code" when it is not open.
- **Fix:** First check whether the desktop app also rewrites `~/.claude.json` (its Code tab may); if it does, keep the match and only change the message to "Claude Code or the Claude app". If it does not, tell them apart by path (`\AnthropicClaude\`, `Claude.app/`) once command lines are read on Windows too (BUG-08 in the first report needs that anyway). For the space case, match `/(^|[\\/])claude(\.exe)?(\s|$)/i` on the whole line.
- **Effort:** S
- **Confidence:** low for the desktop-app part (the name match is certain; whether skipping is wrong depends on what the desktop app writes); high for the path-with-a-space part

### SEC-03 · Medium · A script anywhere in Claude Code's folder is restored without review

- [x] **Where:** `packages/cli/src/agents/claude-code/restore-rules.ts:100-104` (`globalDestination`: `… || isScript(path)`); `packages/cli/src/pull/command-review.ts:226-241` (`scriptsRun` lists a script only when a hook or status line command names it)
- **Problem:** For files in the home folder, a bundle entry is restored only if the setup's own hooks run it (finding 1 of the threat model). For Claude Code's base folder there is no such rule: any path with a script extension that is not in a never-synced folder is accepted. Checked with the real function: `chrome/chrome-native-host.bat`, `local/node_modules/@anthropic-ai/claude-code/cli.js` and `anything/else/run.ps1` all return `{ kind: 'target' }`, and `reviewRunnable` returns nothing for them. Push never produces such entries (it saves a script outside the synced folders only when a hook names it), so only a forged bundle holds them.
- **Why it matters:** `~/.claude/chrome/chrome-native-host.bat` exists on this PC; Chrome starts it for the Claude extension. `~/.claude/local/…/cli.js` is Claude Code itself on PCs with the local install. A compromised PC can put a changed copy in the saved setup. On the next PC:
  - `pull --overwrite` (with or without `--yes`, and **without** `--allow-commands`) replaces the launcher. The threat model says `--yes` alone never accepts new code.
  - An interactive pull shows only "chrome/chrome-native-host.bat already exists here and is different"; "Overwrite all remaining files" takes it along. It is never in the "these run programs" list.
  - A path that does not exist yet is written with no question at all.

  With `--yes` alone the file is kept and the copy is put next to it, so that case is safe.

- **Fix:** In `globalDestination`, apply the home-folder rule: outside `GLOBAL_FOLDERS`, a script is allowed only when `hookScripts.has(path)` (the set already holds base-folder scripts as plain bundle paths, see `hook-scripts.ts:62-64`). Add the `knownState` entries (`local`, `chrome`, `state`, …) to the refused list, as `NEVER_SYNCED` already is. Add restorer tests for the three paths above.
- **Effort:** S
- **Confidence:** high (both functions run with these inputs; the end-to-end pull with `--overwrite` was not run)

### System design

### ARCH-03 · Medium · The CLI refuses any server answer it does not know by heart, and the API has no version

- [x] **Where:** `packages/contracts/src/api/common.ts:59-79` (`ErrorCodeSchema` enum, `ErrorResponseSchema` strict) and `:81`; `packages/contracts/src/api/auth.ts:50-53,66-69,77-79`; `packages/contracts/src/api/bundles.ts:51-66,81-84` (all `z.strictObject`); used by `packages/cli/src/api/http-api-client.ts:97-114` (`parseJson`) and `:117-143` (`failure`)
- **Problem:** Every answer body is parsed with a strict schema, on the client too. An extra field, or an error code that is not in the enum, makes the CLI throw "The server sent an unexpected answer. Is agentnomad up to date?". There is no API version in the path or in a header, and the CLI sends its version only as `User-Agent`, which the server does not read.
- **Why it matters:** The server deploys from `main` within minutes; installed CLIs update when their users feel like it. So today the API can never add a field to a login, list or save answer, or a new error code, without breaking every installed CLI at once. The code already works around this (`routes/bundles.ts:55`: "An existing code, so 1.0 CLIs understand it"; `WRONG_PASSWORD_MESSAGE` is matched as text for the same reason). Each new feature that needs the server (a device list, a storage-used number, password change) will hit it.
- **Fix:** Strict on what is sent, tolerant on what is received:
  - In the client, parse answers with schemas that ignore unknown fields (`z.object(...)`; keep the strict ones for requests on the server). For errors, accept any string code and map unknown ones to a generic `ApiError` that shows the server's message.
  - Add a contract test: "an answer with one extra field still parses", for each answer schema.
  - Optional, cheap now and hard later: have the server read the CLI version (a header such as `x-an-client`) so it can answer "update agentnomad" on purpose.

  The fix only helps CLIs released after it, so it is worth doing before the next server-side feature.

- **Effort:** S
- **Confidence:** high
